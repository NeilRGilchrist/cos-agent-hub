# Patterns

A pattern is a reusable shape — library, service, convention, or scaffold — that subsumes multiple parked ideas and/or recurring active FRs. Patterns exist to capture compounding value: if you've built the same shape three times, the pattern is "extract this once and reuse it."

## When a pattern gets created

Two paths:

1. **From parking-lot clusters.** When 3+ parked ideas share tags, `/patterns` surfaces a candidate pattern that subsumes them.
2. **From active-FR clusters.** When 3+ FRs across 2+ projects share tags or strong title/body similarity, `/patterns` surfaces a candidate pattern. This signal is higher-value because the FRs have already shipped — the pattern is battle-tested.

## Lifecycle

```
proposed ──confirm──▶  accepted ──build──▶  built
    │
    └──reject (with reason)──▶  rejected (won't be re-proposed without explicit override)
```

## Compounding-value discipline

Every pattern must articulate a one-paragraph compounding-value hypothesis: why is the pattern greater than sum of its parts? "These are all about data" is not a hypothesis. "Three projects each built rate-limited HTTP retry from scratch; extracting it as a library would save N hours per future project and give us a single place to fix bugs" is a hypothesis.

## Rejection memory

Rejected patterns store their rejection reason in frontmatter. `/patterns` won't re-propose anything semantically equivalent to a rejected pattern unless you pass `--reconsider`.
